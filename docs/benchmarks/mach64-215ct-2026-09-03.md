## Results
Average FPS: **14.768977** (4475 frames / 303s, `time(NULL)`-based). **No
  established reference exists for this CPU (486DX2-66) + current-build
  combination on Mach64** -- the only prior Mach64 number (~10.4-10.6fps)
  is from a different CPU tier (486DX2-50) and a much older, pre-pacer,
  pre-percentile-work build. **This is the first datum, not a pass/fail.**
1% low: RUNMANIFEST `fps_p50=16.67`, `fps_p95=9.09` -- identical to both
  Cirrus and ViRGE on this build. See Notes.
Simulation rate: locked at 15fps target, pacer-bound, unchanged.
Audio underruns: not instrumented. Two `vcctrl_audio_verdict` checks
  (~35s, ~185s post-launch), both `AUDIO_PRESENT`, music-like. No
  pitch/tempo complaint this run (operator wasn't actively monitoring
  audio this time -- absence of a report is not evidence the ViRGE-leg
  KVM-audio caveat didn't recur or did; genuinely unknown either way).
Peak memory: not measured.
Notes:
- **Correctness gate: initially FAILED, then fixed and PASSED -- full
  story below, this is the headline finding of this leg.** The first
  launch attempt negotiated **512x384 16bpp**, not 640x480 -- a mode
  this specific rig's VGA capture stick cannot lock onto at all (an
  operator decision from 2026-08-19, `docs/VIDEO-SWAP.md` in the
  `vcctrl` repo, predating this campaign: "stop running the mach64 in
  512x384, it won't display in our harness, it must be 640x480"; that
  decision's enforcement lives in vcctrl's own scripted harness path,
  which doesn't cover dossage's by-hand DOS-prompt launch). Capture
  stick reported `frozen`; the independent hardware camera confirmed
  the physical monitor genuinely synced but squashed the image into a
  thin horizontal strip. **Not a dossage bug**: root-caused to core
  SDL3's `SDL_GetClosestFullscreenDisplayMode()` (vendored, untouched by
  any DOS-layer or dossage patch) tie-breaking on aspect ratio -- 320x240
  (the request), 512x384, and 640x480 are all exactly 4:3, so it's a
  three-way tie, and the algorithm always keeps the smallest qualifying
  candidate. Confirmed **not** caused by dossage's own
  `PIN_WINDOW_TO_NATIVE_MODE` hint (that hint's suppression code cannot
  even fire on the very first mode-set -- `current_mode.internal` is
  still NULL at that point, verified directly in the DOS backend
  source). **This exact scenario is the documented motivating case for
  the shared layer's `SDL_HINT_DOS_FORCE_MODE_ID` hint** (its own header
  doc comment in `vendor/SDL/include/SDL3/SDL_hints.h` names this
  precise 512x384-vs-640x480 tie-break). doskutsu hit the *identical*
  bug on the *identical* Mach64 215CT/UniVBE 6.70 combination (their own
  `docs/internal/BOOT.md`, dated 2026-08-19 -- the same investigation
  this rig's own operator note traces to) and handles it the same way:
  an ad hoc hint invocation for specific benchmark phases, never baked
  into the standard boot path, with the actual standing mitigation being
  harness-level (their own vcctrl-cell "no 512x384" rule). **Fix
  applied**: `SET SDL_HINT_DOS_FORCE_MODE_ID=0x0111` before launching
  `DOSSAGE.EXE` -- forces 640x480 as the only enumerated candidate,
  confirmed landing correctly (`DOSVESA-MODESET: id=0x0111 640x480
  16bpp`), fails safe if the mode weren't available. Post-fix: capture
  stick itself went from `frozen` to `locked` (independent confirmation
  512x384 really was the out-of-range mode), gameplay correctly
  proportioned, visual pixel/color comparison against
  `docs/screenshots/dossage-gameplay.png` clean -- same structural
  match, same VGA-capture dimming pattern as the other two legs, no
  corruption. **This card has a documented history of real-hardware-only
  video corruption on this exact port** (root-caused and fixed port-side
  in patch 0003, XRGB8888 render surface, confirmed resolved via
  pixel-diff at the time) -- nothing here reproduces that pattern.
  **This fix (`SET SDL_HINT_DOS_FORCE_MODE_ID=0x0111`) needs to be part
  of any future Mach64 launch procedure on this rig** -- it is a launch-
  environment requirement, not a one-time workaround; dossage has no
  boot-menu/launcher infra yet to bake it in automatically (see
  `profiles/dossage.yaml`'s own TBD notes on this), so it must be set by
  hand (or scripted) every time until that infra exists.
- **Three-way cross-card, cross-chip confirmation of the bimodal pacing
  finding.** `fps_p50=16.67` (~60ms), `fps_p95=9.09` (~110ms), and a
  near-zero reject rate (0.27%, matching both other legs on this build)
  now hold identically across Cirrus (banked, different chip family),
  ViRGE (LFB), and Mach64 (LFB, yet another different chip family). This
  is no longer just "not video-path-related" -- it's now "not
  video-card-related at all," which points squarely at something shared
  across all three runs: the same CPU (486DX2-66) and the same build. A
  standalone `Time::getCurrentTime()`/pacer-timing probe remains queued,
  not yet run, to identify the actual mechanism (leading, unconfirmed
  hypothesis: the ~110ms cluster is close to 2x the PC BIOS/PIT tick,
  ~54.925ms; the ~60ms cluster's source is still unidentified).
- Plain average (14.77fps) happens to land in the same ~14.77-14.82fps
  band as both Cirrus and ViRGE runs on this build -- interesting given
  the much larger spread in the old, pre-pacer-work figures (Mach64 at
  a different CPU tier was ~10.4-10.6fps; Cirrus/ViRGE gap was
  meaningful too) -- consistent with `lockedFrameRate=15` acting as a
  shared ceiling all three cards now approach similarly under the
  current pacer.
- RUNMANI.LOG for this leg contains four blocks total (two short
  correctness-gate launches, pre- and post-fix, plus this leg's two real
  lives) -- the two gate-check blocks are not benchmark data, included
  in the raw log for completeness but not reported as results here.
