up, per the operator: ViRGE"), and the first ViRGE result run against

## Results
Average FPS: **15.016779** (4475 frames / 298s, `Game time = 4:58`,
  captured verbatim from `FPS.TXT`). **PASS against the 486DX2-50 KPI
  line (14.90fps, `docs/BENCHMARK-PLAN.md`'s Round 3 result) with real
  margin.** Frame-time sample notes: "4474 used, 0 rejected
  non-positive, 0 rejected below 0.001s, 0 rejected above 5.0s" -- clean,
  matching the 0-reject signature the 486DX2-66/486DX2-50 legs have
  shown since patch `0035`.
1% low: RUNMANIFEST `fps_p50=15.00`, `fps_p95=14.80` -- identical to
  Round 3's Mach64+486DX2-50 result (`fps_p50=15.00`, `fps_p95=14.80`,
  both G1 and G2) on the same CPU tier and same merged build.
Simulation rate: locked at the 15fps design ceiling, pacer-bound -- see
  Notes for the cross-card confirmation this implies.
Audio underruns: not instrumented. `AUDIO_PRESENT` confirmed multiple
  times during life 1 (wide spectral spread, `tone_like=false` --
  real music, not a hum). Unlike the 486DX2-66 ViRGE leg
  (`virge-86c375-2026-09-03.md`), this run used the audio-tier-matched
  build, so there is no pitch/tempo mismatch to caveat this time.
Peak memory: not measured.
Notes:
- **Bit-for-bit match to Round 3's Mach64+486DX2-50 G2 life**: same
  frame count (4475), same average fps to six decimal places
  (15.016779), same percentiles (`fps_p50=15.00`/`fps_p95=14.80`). Two
  structurally different video paths (ViRGE LFB at 320x240x16 vs.
  Mach64's forced 640x480x16) on the identical CPU/build producing an
  identical per-frame timing signature is strong further confirmation
  (on top of the pre-existing five-axis pacer-timing finding, see
  `docs/PACER-TIMING-INVESTIGATION.md`) that this CPU tier's pacing is
  governed by the BIOS/PIT tick and the fix's own correctness, not by
  anything video-card-specific. Also directly answers the open question
  the 486DX2-66 ViRGE leg's Notes raised: the audio-tier fix's fps
  benefit **does** transfer cleanly to ViRGE's LFB path, not just
  Mach64's -- untested before this run, now confirmed.
- **Data-collection incident, corrected, not a build/hardware problem.**
  The first launch used a bare `DOSSAGE` command with no output
  redirect, so the `printf("Frame rate = ...")` line (the primary
  Average FPS metric every leg in this campaign reports) only ever hit
  the DOS console device and was unrecoverable after the fact (DOS text
  mode has no scrollback, and the CWSDPMI exit banner that prints after
  it would have scrolled it off-screen regardless). RUNMANIFEST
  percentiles from that first life were still captured
  (`fps_p50=15.00`/`fps_p95=14.80`, matching this run's) since that
  writes to a file regardless of console redirect. Re-ran one clean life
  with `DOSSAGE > FPS.TXT` to capture the average -- the figures reported
  above are from that second, correctly-captured life.
  `docs/rig-runbook.md` now notes the redirect requirement (section 4)
  so this doesn't cost a round on a future leg.
- **Staging incident, corrected, functionally a no-op.** The operator's
  session initially staged this build to `C:\DOSKUTSU` (the harness's own
  unrelated QA game directory) after misreading the boot banner text;
  `DOSSAGE.EXE` page-faulted immediately there (`eip=001a1d4a`), expected
  given the foreign environment rather than a build defect. Corrected by
  deleting everything added to `C:\DOSKUTSU` (confirmed via `DIR` back to
  its original file list) and re-staging clean to `C:\DOSSAGE`,
  hash-verified. One residual, deliberately not undone: `C:\DOSKUTSU`'s
  own `CWSDPMI.EXE`/`.DOC` got overwritten with dossage's copies of the
  same files -- both ports vendor the identical upstream CWSDPMI r7
  build (per doskutsu's own `THIRD-PARTY.md`), so this is functionally a
  no-op, not a corruption, but is flagged here in case another session
  using this rig (`15fps`, `sdldos`) notices the file timestamp changed
  and wonders why.
- **UVCONFIG-not-yet-run gate did its job.** Caught pre-cell via the
  VBE-string field on a fresh scan, exactly the failure mode
  `docs/rig-runbook.md` documents from the 2026-09-03 Cirrus->ViRGE
  swap. No cell was run against the stale driver; the operator was
  pinged directly and the re-scan confirmed the fix before staging
  proceeded. Zero rounds lost to this, unlike the 2026-09-03 precedent.
- Visual: launch matched `docs/screenshots/dossage-gameplay.png` --
  same squashed-strip aspect (this rig's known Mach64/ViRGE capture
  characteristic; not corruption), same tile texture, character sprite,
  and palette. Character aging observed through the life as expected.
  Clean two-Escape exit confirmed via the hardware camera (primary VGA
  capture cannot lock DOS text mode) -- clean `C:\DOSSAGE>` prompt with
  CWSDPMI's own exit-stats banner visible.
- `SDLDBG.LOG`: `DOSVESA-CTRL: VBE 3.0 total_vram=4096_KB
  oem_sw_rev=0x0607`, `oem_string='Universal VESA VBE 6.70'`,
  `oem_vendor='SciTech Software, Inc.'`; `cirrus-lfb-aperture-bug: NOT
  detected -> LFB path remains enabled`; `DOSVESA-MODESET: id=0x01D9
  320x240 16bpp has_lfb=1 use_lfb=1 banked=0 lfb_addr=0x78000000`. No
  `SDL_HINT_DOS_FORCE_MODE_ID` needed or set -- that requirement is
  Mach64-specific (the aspect-ratio tie-break bug); ViRGE negotiates its
  native 320x240 directly.
- Rig-daemon input-pacing note (not a dossage finding, recorded here
  for continuity): `vcctrl-c3` found this rig's `pace_s` had reset to
  0.012 (tuned for faster CPUs) and was corrupting long typed commands
  on this 486DX2-50, per the vcctrl repo's `FINDINGS.md` sec.43. Bumped
  back to 0.04 and confirmed clean before this session's identity scan.
  Flagging in case it resurfaces on a future 486DX2-50 leg.
