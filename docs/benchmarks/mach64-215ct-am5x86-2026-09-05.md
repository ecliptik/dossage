Am5x86-133 datum (15.016779fps,

## Results
Average FPS: **14.966555** (4475 frames / 299s, `Game time = 4:59`,
  captured verbatim from `FPS.TXT`). **PASS.** Frame-time samples:
  "4474 used, 0 rejected any category" -- clean.

  **Lands on the "one second over" pattern, same as the two Cirrus
  486DX2 legs -- but this CPU tier (Am5x86-133) hit the clean
  298s/15.016779fps signature on BOTH ViRGE and Cirrus earlier this
  campaign.** This complicates, rather than confirms, the Cirrus
  sweep's own "clean CPU-tier boundary, not a gradient" conclusion (see
  `docs/benchmarks/cirrus-cl-gd5434-am5x86-2026-09-05.md`) -- that
  conclusion held within the Cirrus data alone, but Mach64+Am5x86-133
  now shows the effect that Cirrus+Am5x86-133 did not, at the identical
  CPU tier. **Revised picture, see Notes**: this looks less like a
  deterministic function of CPU tier and more like boundary-adjacent
  jitter that different video paths push closer to or further from.
1% low: RUNMANIFEST `fps_p50=15.00`, `fps_p95=14.96` -- matches every
  other Am5x86-133 leg's percentiles almost exactly regardless of which
  side of the 298/299 boundary the average landed on. Zero
  `critical_count`/`warn_count`.
Simulation rate: pacer-bound at the 15fps design ceiling, comfortably.

Notes:
- **Real video-driver hazard hit and recovered mid-session, not a data
  problem.** ~75s into the first launch attempt, the physical monitor
  showed a genuine OUT OF RANGE (hardware-camera-confirmed, the real
  thing, not a capture-stick freeze) despite `SDLDBG.LOG` showing the
  correct logical mode negotiated (`id=0x0111 640x480 16bpp`). Root
  cause: UniVBE was still running the driver UVCONFIG generated for the
  prior Cirrus swap -- the mode *ID* matched Mach64's requirement, but
  the actual CRTC timing UniVBE was shimming was Cirrus's, hence the
  physical monitor rejecting the signal. `total_vram=1024_KB` (Cirrus's
  figure) in that run's log and `dinspect`'s own stale "1 MB" reading
  were both the same underlying symptom, not two separate bugs.
  Recovered cleanly: one Escape quit the in-progress life (game was
  in-life, not at the title, so Escape triggered a normal quit rather
  than starting a new life), no hang, no power cycle. UVCONFIG re-run
  by the operator; fresh scan confirmed the fix (`total_vram=2048_KB`)
  before the recorded run above.
- **Revised understanding of the "one second over" effect.** The
  Cirrus sweep's conclusion -- a clean CPU-tier boundary, present at
  both 486DX2 tiers and absent at both faster tiers -- does not survive
  this data point: Am5x86-133 shows the effect on Mach64 but not on
  Cirrus or ViRGE. Two candidate explanations, neither confirmed via
  dedicated instrumentation:
  1. **Framebuffer size, not banked-vs-LFB.** `vcctrl-c3`'s hypothesis:
     Mach64 runs LFB here (`use_lfb=1 banked=0`, ruling out "banked
     path" as the necessary condition, since Cirrus's effect was
     originally framed around its banked path specifically), but at
     640x480x16bpp Mach64 moves 614400 bytes/frame
     (`WAVE16-MODESET raw_bytes_per_frame=614400`) versus ViRGE and
     Cirrus's shared 320x240x16bpp, 153600 bytes/frame -- 4x the pixel
     data regardless of video-path type. A per-frame cost proportional
     to bytes moved would explain why Mach64 (largest framebuffer) is
     the most exposed card, Cirrus (banked, same pixel count as ViRGE
     but slower per-byte due to bank switching) is next, and ViRGE
     (LFB, smallest framebuffer) never shows it at all across any CPU
     tier tested.
  2. **Boundary-adjacent run-to-run jitter, not a deterministic
     per-pairing outcome.** Re-reading `docs/benchmarks/mach64-215ct-486dx2-50-round3-2026-09-04.md`
     with this question in mind: that leg's own three measured lives on
     the *identical* 486DX2-50+Mach64 pairing and build split
     298s/299s -- G1 (299s, 14.966555fps), G2 (298s, 15.016779fps), D3
     (299s, 14.966555fps, frame-for-frame identical to G1). Two out of
     three lives on one fixed hardware/build combination landed on
     opposite sides of the rounding boundary. That is hard to reconcile
     with "this pairing deterministically produces X" for *any* pairing
     this close to the boundary -- it argues the true underlying
     average frame period sits close enough to the 66.667ms design
     ceiling that small run-to-run timing variance (plausibly tied to
     the same DOS-tick-phase-dependent quantization
     `docs/PACER-TIMING-INVESTIGATION.md` already root-caused for the
     bimodal per-frame clusters) can tip a single life's total duration
     across the integer-second reporting boundary either way.
  These aren't mutually exclusive: framebuffer size could set how close
  to the boundary a given CPU/card pairing sits on average, while
  per-life jitter decides which side any individual measured life lands
  on. Distinguishing them properly would need either several repeat
  lives per pairing (to get a real distribution instead of 1-3 samples)
  or a dedicated diagnostic build instrumenting per-frame blit cost
  directly (the same approach the 486DX2-50 Phase 2 campaign used) --
  not pursued further here since nothing here threatens the KPI at any
  tier tested. Flagging as an open characterization question, not an
  action item.
- A one-off log-fetch hazard (15-character BIOS keyboard-buffer
  truncation, `C:\MTCP\VCCHK.B`) hit during this session -- the rig
  daemon's own watchdog caught it and recovered to menu default rather
  than typing blind; a plain retry fetched cleanly. Not linked to
  Am5x86-133's CPU pace (this chip has never needed the `pace_s` bump
  486DX2-50 did) -- treated as an isolated one-off, not a new hazard
  pattern, but recorded here in case it recurs.
- Visual: matched `docs/screenshots/dossage-gameplay.png`, correctly
  rendered at 320x240 windowed within the 640x480 mode, no corruption.
  Clean two-Escape exit confirmed via the hardware camera.
- `SDLDBG.LOG` (post-UVCONFIG-fix, the recorded run):
  `DOSVESA-CTRL: VBE 3.0 total_vram=2048_KB`, `oem_string='Universal
  VESA VBE 6.70'`; `LFB-decision #1: ... -> use_lfb=1`;
  `DOSVESA-MODESET: id=0x0111 640x480 16bpp has_lfb=1 use_lfb=1
  banked=0 lfb_addr=0x78000000`; `WAVE16-MODESET: mode=0x0111 640x480
  raw_bytes_per_frame=614400`.
