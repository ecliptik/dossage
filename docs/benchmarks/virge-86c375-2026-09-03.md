## Results
Average FPS: **14.817881** (4475 frames / 302s, `time(NULL)`-based)
1% low: RUNMANIFEST `fps_p50=16.67`, `fps_p95=9.09` -- **exact match to
  both Cirrus runs on this same build**, see Notes.
Simulation rate: locked at 15fps target, pacer-bound, unchanged.
Audio underruns: not instrumented. Two `vcctrl_audio_verdict` checks
  (~35s and ~185s post-launch), both `AUDIO_PRESENT`, music-like
  (mean_db -34.89, then -27.56). See the pitch/tempo caveat in Notes --
  unrelated to this metric (presence, not correctness).
Peak memory: not measured.
Notes:
- **AUDIO-TIER MISMATCH BUG, found 2026-09-03 -- affects this run,
  correcting the record rather than leaving it implicit (see also the
  specific correction further down in these Notes -- this run's own
  operator-observed pitch/tempo anomaly IS this bug, not a KVM
  artifact).** The committed `vendor/passage/gameSource/music/SONG.WAV`
  is the low-tier render (11025Hz mono, 2998844 bytes), but this build
  used `AUDIO_TIER=high` (22050Hz stereo). `musicPlayer.cpp` loads the
  WAV via `SDL_LoadWAV()` but never uses the returned spec --
  `audioFormat.freq`/`channels` come from the compile-time tier
  constants instead, so a mismatched file plays at the wrong rate (that
  exact failure mode, "wrong-speed, wrong-pitch playback," is documented
  in that file's own code comment). Confirmed present on the physical
  target (`DIR` = 2,998,844 bytes) and in this build's `build/stage/`.
  **`AUDIO_PRESENT` above only confirms audio was playing, not that it
  played at the correct pitch/tempo.** **Correction, 2026-09-04**: this
  file originally predicted fps "is not expected to be affected" here --
  that was wrong, not just unconfirmed, corrected rather than left
  standing. Round 1
  (`docs/benchmarks/mach64-215ct-486dx2-50-round1-2026-09-04.md`)
  measured a real, large fps effect from this exact audio-tier mismatch
  (~4.75fps between correctly-staged high- and low-tier builds) on
  486DX2-50, a CPU with little pacer slack. This leg's CPU (486DX2-66)
  has considerably more slack against the 66.67ms budget, so the same
  effect may be smaller here, but it was never independently re-measured
  on this CPU/card combination -- don't assume this run's recorded fps
  is unaffected just because the CPU has slack; treat it as untested,
  not confirmed clean. `build_sha12` does not cover this -- it hashes the
  vendor tree's committed (always-low-tier) file, not what actually gets
  staged, so this bug is invisible to the build fingerprint. Fixed and
  landed on `main` 2026-09-04 (merge `2881cfc`; patches `0036`,
  `0038`-`0041` -- `0037` was a temporary diagnostic, removed by
  `0038`; the `make stage` guard also landed). **Re-measured on this
  exact CPU/card combination, 2026-09-04: PASS, 15.016779fps** under
  the merged fix build (`build_sha12=a5e9835f12e7`) -- no longer
  untested. See `docs/benchmarks/virge-86c375-486dx2-66-2026-09-04.md`.
- **PASS.** 14.817881fps is 0.12fps from the ~14.94fps Cirrus-era
  reference, inside the 0.3fps band -- and notably, this is *closer* to
  the reference than either Cirrus run under this exact build family,
  even though ViRGE's LFB path was historically faster than Cirrus's
  banked path in the pre-pacer-work figures (14.16-14.5 ViRGE vs.
  13.88-13.94 Cirrus, both prior builds). Under the current build, both
  cards land in essentially the same ~14.77-14.82fps band -- consistent
  with `lockedFrameRate=15` acting as a shared ceiling that the pacer
  work has both cards approaching similarly, closing the gap the
  earlier, less-tuned pacer left between banked and LFB paths.
- **Cross-card confirmation of the bimodal pacing finding: identical
  numbers on a structurally different video path.** `fps_p50=16.67`,
  `fps_p95=9.09`, and a near-zero reject rate (12/4475 = 0.27%, matching
  Cirrus's 0.22% on the same build) all reproduce exactly on ViRGE's LFB
  path after being found on Cirrus's banked path. **This rules out the
  video-access path (banked vs. LFB) as the cause** -- the same two
  discrete clusters (~60ms, ~110ms) appear regardless of how the
  framebuffer is written, which strengthens (does not yet confirm) the
  working hypothesis that this is a CPU/system-timer-level effect (e.g.
  PC BIOS/PIT tick interaction), not anything video-card-specific. Still
  queued as a standalone `Time::getCurrentTime()`/pacer-timing probe,
  not yet run.
- **CORRECTION, 2026-09-03: the pitch/tempo observation below was
  mis-attributed at the time. It is the audio-tier mismatch bug
  described at the top of these Notes, not a KVM artifact.** Original
  text, kept rather than deleted, per this project's "correct the record
  explicitly" discipline: "Caveat, observed but not attributed to this
  build. The operator, watching live via the KVM, reported the music
  sounding wrong (pitch too high, tempo too fast) partway through life
  1. Evidence points away from a dossage/DOS-target bug: muting/unmuting
  the KVM's own browser audio caused the song to audibly restart, which
  the DOS target's own SB16/OPL3 hardware has no mechanism to react to
  -- consistent with a known characteristic of the KVM's browser
  `AudioContext` resampling path... rather than a dossage-side defect."
  That reasoning was plausible from what was observable at the time (the
  mute/unmute-restart behavior is real and unrelated), but the actual
  cause was sitting on the card the whole time, checkable with one `DIR`
  command nobody ran until the bug was found from a different angle
  entirely (a source-code review of `musicPlayer.cpp`, not a rig
  observation). "Pitch too high, tempo too fast" is exactly what a mono
  11025Hz file played back as if it were stereo 22050Hz sounds like --
  this leg's own live-operator observation is now the single clearest
  piece of first-hand evidence in the whole campaign that this bug was
  real and audible, not just a byte-count mismatch on disk.
