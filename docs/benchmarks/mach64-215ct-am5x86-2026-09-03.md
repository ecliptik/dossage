# Benchmark

## Hardware
CPU: AMD Am486/5x86 family (operator installed the Am5x86-133 part).
  **Identity note, read before trusting the label**: dinspect's own
  detection read `CPU Speed: ~100 MHz` (not 133) and
  `Floating Point Unit: no`. The FPU reading is confirmed WRONG by a
  positive functional test, not just disputed: a dedicated pre-run gate
  (burst-watched the first ~20s of a real launch) showed a completely
  normal load, correctly rendered gameplay by ~t+5s, and normal character
  aging by t+20s -- Passage/minorGems is floating-point-heavy throughout
  (`double` age/position/scaling math), so a genuinely FPU-less chip with
  no software emulation configured would very likely have crashed within
  the first second or two, not run cleanly. Treat the FPU as present and
  working. The speed reading is unconfirmed either way -- likely
  dinspect's simple timing-loop detection being imprecise on this less-
  common (non-Intel) chip, consistent with this leg's own fps result
  being the fastest of the whole campaign (see Results) despite the
  lower speed reading -- but not independently verified against a second
  method. Chipset/vendor ID correctly reads AMD, not confused with Intel
  or a different vendor, so the CPU swap itself clearly happened as
  intended.

  **Root cause closed 2026-09-03 (vcctrl's `dinspect` session)**: the FPU
  bug was a real dinspect defect, not a measurement fluke --
  `get_fpu_status()` in dinspect's `src/cpu.c` only read the INT 11h BIOS
  equipment-word FPU bit, which many BIOSes populate from a CMOS
  setup/jumper-sensed value carried over from an earlier boot rather than
  a live probe -- exactly the kind of thing that goes stale after a CPU
  swap without a CMOS reset. dinspect's separate "CPU Features" field
  (CPUID leaf 1 EDX bit 0) already had the right answer on the same scan,
  just not surfaced in the "Floating Point Unit:" line. Fix: prefer
  CPUID whenever available, fall back to INT 11h only on pre-CPUID
  hardware. Not yet committed as of this writing. The ~100MHz-vs-133MHz
  speed question remains genuinely open -- dinspect's speed-estimate
  calibration is anchored to two Intel 486DX2 (2x-multiplier) data
  points and this is a 4x-multiplier AMD part with different cache/
  pipeline behavior, a plausible systematic undercount, but the project
  correctly declined to touch the calibration on one anecdotal reading
  with no independent cross-check (Am5x86 has no TSC). Still first-datum,
  still unconfirmed.

  **Speed question also closed, 2026-09-03, same day, upstream on
  dinspect's own master.** Both fixes landed together: FPU detection now
  prefers CPUID (as above), and AMD family-4 CPU speed recognition --
  previously too generic, collapsing into one bucket and falling through
  to a generic MHz-snap table -- now reads AMD's actual CPUID model value
  (0xE/0xF = Am5x86, snapping to its real 133 or 160 MHz grades instead
  of a raw loop-timing guess). Confirms the fix directly: this leg's raw
  ~100MHz loop estimate now snaps to 133, matching the label. **Both
  discrepancies in this leg's CPU identity were dinspect detection bugs,
  now fixed -- not properties of the physical chip.** The chip really is
  a working Am5x86-133 with a functioning FPU; nothing about this run's
  own fps result needs re-reading in light of this, since the actual
  hardware never changed, only the tool's ability to describe it
  correctly. **Independently re-confirmed live, same day**: vcctrl-c3
  deployed the fixed `DINSPECT.EXE` (commits `cc43ae3`/`33096ea`) to the
  same physical Am5x86-133 and re-scanned -- `CPU: AMD Am5x86`,
  `CPU Speed: ~133 MHz`, `Floating Point Unit: YES`. Both fields now
  correct, fully closed, no longer just inferred.

## Results
Average FPS: **15.016779** (4475 frames / 298s) -- **the fastest run of
  the entire campaign**, faster than both 486DX2-66 (~14.77-14.82) and
  486DX2-50 (13.69) despite dinspect's own speed reading (~100MHz) being
  lower than either Intel tier's clock. Whatever this chip's real clock
  is, it's clearly outperforming both 486DX2 tiers on this workload --
  plausible given the Am5x86's own "P75" (Pentium-75-class performance)
  positioning, but not independently confirmed against a verified clock
  reading. **No established reference for this CPU/build/card
  combination** -- first datum, not a pass/fail.
1% low: RUNMANIFEST `fps_p50=16.67`, `fps_p95=9.09` -- unchanged, see
  Notes.
Simulation rate: 15.016779fps sits essentially AT the design ceiling
  (`lockedFrameRate=15`) -- this chip has real pacer slack, unlike the
  486DX2-50 result.
Audio underruns: not instrumented. `AUDIO_PRESENT` confirmed (folded into
  the FPU-diagnostic watch, plus a mid-run check).
Peak memory: not measured.
Notes:
- **AUDIO-TIER MISMATCH BUG, found 2026-09-03 -- affects this run,
  correcting the record rather than leaving it implicit.** The committed
  `vendor/passage/gameSource/music/SONG.WAV` is the low-tier render
  (11025Hz mono, 2998844 bytes), but this build used `AUDIO_TIER=high`
  (22050Hz stereo). `musicPlayer.cpp` loads the WAV via `SDL_LoadWAV()`
  but never uses the returned spec -- `audioFormat.freq`/`channels` come
  from the compile-time tier constants instead, so a mismatched file
  plays at the wrong rate (that exact failure mode, "wrong-speed,
  wrong-pitch playback," is documented in that file's own code comment).
  Confirmed present on the physical target (`DIR` = 2,998,844 bytes) and
  in this build's `build/stage/`. **`AUDIO_PRESENT` below only confirms
  audio was playing, not that it played at the correct pitch/tempo.** fps
  is not expected to be affected (the audio-pump callback processes the
  same byte count per pump call regardless of what the bytes represent),
  not independently confirmed either. `build_sha12` does not cover this
  -- it hashes the vendor tree's committed (always-low-tier) file, not
  what actually gets staged, so this bug is invisible to the build
  fingerprint. Fix in progress (`15fps` session, patches `0036`/`0037`
  plus a hard `make stage` guard, separate `dx2-50-15fps` worktree, not
  yet landed in this tree).
- **CPU identity has a real, only-partially-resolved caveat -- read the
  Hardware section above before treating "Am5x86-133" as a confirmed
  label.** The FPU question is resolved (present, working, confirmed by
  successful float-heavy execution, not just asserted). The clock-speed
  question is not -- dinspect's ~100MHz reading vs. the "133" label are
  both plausible-but-unverified; this run's own fastest-of-campaign
  result is circumstantial evidence for a genuinely fast part, not proof
  of either number.
- **Fifth independent-axis confirmation of the bimodal pacing finding.**
  `fps_p50=16.67`/`fps_p95=9.09` now hold identically across 3 video
  chip vendors (Cirrus, ViRGE, Mach64) AND 3 CPUs (486DX2-66, 486DX2-50,
  Am5x86-133) -- five axes, same two numbers every single time, despite
  the plain average spanning a real 13.69-15.02fps range across just the
  three CPU results. This is now about as strong as full-game evidence
  gets for a fixed-frequency mechanism independent of card, CPU vendor,
  and CPU clock speed. See `docs/PACER-TIMING-INVESTIGATION.md` for the
  standing investigation brief -- not chased further as part of this
  benchmark run.
- Reject rate 13/4475 = 0.29%, consistent with every other leg's clean
  0.2-0.3% range (the sole exception remains 486DX2-50's 0/4475).
- A stdout-file-naming mixup happened during data collection (this run's
  real output landed in `FPUSTDO.TXT`, carried over from the earlier FPU
  diagnostic launch, rather than the usual `RUNSTDOU.TXT` name) --
  caught and corrected before reporting (`Game time = 4:58` cross-checked
  against `duration_s=298` to confirm the right file), not a data
  problem, just a naming inconsistency worth knowing about if grepping
  for this leg's raw files later.
- Visual pixel-diff not repeated this run (already established as
  CPU-independent on the 66MHz Mach64 leg); the FPU-diagnostic watch's
  description of correctly-rendered gameplay is the closest thing to a
  visual check this leg has.
- `vcctrl_verify_input`'s Caps Lock LED round-trip read "no LED change"
  during the FPU-diagnostic watch despite simultaneous correctly-
  rendered gameplay and confirmed audio -- read as the game polling the
  keyboard controller directly rather than through DOS's normal LED-
  update path (plausible, not itself investigated), not as a hang. Not
  seen on any other leg because this is the first time input-verify was
  checked mid-game rather than only video/audio.
