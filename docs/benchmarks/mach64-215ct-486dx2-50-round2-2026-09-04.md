# Benchmark -- Round 2: Phase 2 (device-native audio, L1c; 16bpp blowup, L2), real-hardware validation

Validates `15fps`'s Phase 2 build work against real hardware, on the same
486DX2-50 + Mach64 rig as Round 1
(`docs/benchmarks/mach64-215ct-486dx2-50-round1-2026-09-04.md`). Owned by
the `15fps` peer session (worktree `/home/claude/git/dossage-dx2-50`,
branch `dx2-50-15fps`); driven on the rig by `vcctrl-c3`; coordinated/
recorded by this session. Rig stood down at the end of Round 1 with the
CPU deliberately left at 486DX2-50; this round is a cold boot.

## Notes

- **E0 -- invalid, but not wasted: found a real video-mode gap and a
  visual-corruption false alarm, both resolved.** This round started
  with a cold boot, and the DOS environment was empty -- the operator's
  first launch of `C:\DX50E\DOSSAGE.EXE` never had
  `SET SDL_HINT_DOS_FORCE_MODE_ID=0x0111` set, so the Mach64 negotiated
  its unforced default, `512x384` (`id=0x01D4`, confirmed via
  `DOSVESA-MODESET`). This is a mode this rig's primary VGA capture
  stick cannot lock (reads `frozen`/black), which combined with PS/2
  input appearing dead (`vcctrl_verify_input`'s LED round-trip is not a
  valid liveness test while SDL/DOSSAGE owns the keyboard controller --
  it doesn't toggle LEDs) and real power draw (22.3W, well above
  standby) to initially look exactly like the RDTSC-wedge-under-EMM386
  hang from the earlier CPU-identity investigation. **False alarm,
  confirmed by the operator directly** ("I am able to move the character
  around, so system isn't hung") -- no power cycle happened, no state
  lost. Separately, a user watching the physical monitor spotted real,
  static visual corruption on this same launch: two horizontal bands of
  green dashed/dotted glyph-like marks above the (correctly-rendered)
  "Passage" title logo, confirmed via two camera shots ~25s apart
  (identical both times, ruling out the progressive S3-ViRGE-style
  corruption bug from earlier campaign history). **Root-caused as a
  512x384-mode-specific artifact, not a patch 0040 regression**: E1's
  title screen in the validated `0x0111` mode showed no banding at all.
  The title logo rendering correctly in E0 was itself evidence 0040 was
  fine even before E1 confirmed it -- 0040 only changes how the title
  image's own pixels are packed, and those pixels looked right; the
  banding sat entirely outside the image. The specific mechanism
  (leftover VRAM/text-mode content not cleared in this never-before-
  validated mode) was not conclusively pinned down -- E0's `SDLDBG.LOG`
  showed no pitch/padding mismatch (`raw_bytes_per_frame` ==
  `padded_bytes_per_frame` == 393216, `pitches_match=1`), ruling out that
  specific theory, but the true cause remains an open item (see below).
  E0's own RUNMANIFEST data (duration_s=303, fps_p50=15.00, fps_p95=14.09)
  is not treated as a datum -- hand-played, wrong mode, invalid by design.
- **Title-wait, not tick loss, explains the large wall-clock offsets --
  see the pacer-timing correction below.** E1's launch-to-title bracket
  was 433s against 302s of Game time (a 131s offset); D2's title-to-
  gameplay transition, isolated via `vcctrl_timeline` polling, bracketed
  to [92.6s, 105.8s] specifically (notably longer than E1's, where
  gameplay was already visible by t+50s) -- consistent with ordinary
  startup and title-wait variability, not a clock artifact. E2's
  transition data (byte-size/pixel-change signature from the capture
  ring, not directly visually confirmed) showed a single abrupt scene
  change at delta+94.6-94.8s with no distinguishable separate title-dwell
  period beforehand -- ambiguous, but consistent with the theory that the
  first life can start on a spurious joystick event (`"Found 1
  joysticks"` appears in every run's `STDOUT.TXT`, and a floating
  gameport can deliver a button event at an unpredictable moment) rather
  than waiting for a real keypress.
- **THE decisive result: D2's in-game CMOS RTC witness measured zero
  clock loss, refuting Round 1's tick-loss theory.** `"RTC elapsed = 304
  s (engine time(NULL) = 304 s; engine clock gained 0.0%)"` for the real
  life -- the independent 32.768kHz-crystal RTC clock agrees with the
  engine's own `time(NULL)`-based clock exactly. (Trailing 2-Escape
  block: `"RTC elapsed = 7 s (engine time(NULL) = 8 s; engine clock
  gained -14.3%)"` -- short-block noise at that duration, not a separate
  finding.) **There is no clock loss on this rig.** Round 1's
  high-tier fps figures stand as measured, not as upper bounds; see
  `docs/PACER-TIMING-INVESTIGATION.md`'s corrected closing section for
  the full write-up of this correction.
- **D2's per-stage diagnostic (`STAGEDBG.LOG`, from the same scratch
  branch as the RTC witness, not in the patch series) locates the
  remaining ~5.7s/life shortfall against the 298.3s ideal 15fps life.**
  Steady state is clean -- `pump_avg` is 0.00-0.74ms across most
  windows, `blowup_avg` is ~3.63-3.64ms (down sharply from Round 1's
  ~11.85ms, confirming patch 0040 works as designed), `pacer_avg` ranges
  12.71-21.27ms. But three windows (0, 6, and 13) spike to 8.8-9.78ms of
  `pump_avg` -- these align with the song's loop points (song length
  136s). **Root cause**: the shared platform layer's silence-detect
  throttle (`SDL_HINT_DOS_SILENCE_DETECT`, doskutsu's `SDL/0054`) skips
  the ring write for an all-silent audio chunk and sleeps 10ms as a
  throttle; during the song's quiet passages, with nothing written to
  the ring, the engine's audio pump keeps calling every frame, and every
  cooperative pacer yield pays that 10ms. Three windows x 300 frames x
  ~5ms over budget (plus resync forgiveness) accounts for the full
  5.7s/life shortfall (298.3s ideal vs. ~302-304s measured). Fix: a
  one-line game-side hint (`SDL_HINT_DOS_SILENCE_DETECT=0`) before
  `SDL_Init` -- no shared-layer change needed, reproducible in DOSBox-X
  for local verification. Queued as `patches/passage/0041`, tested in
  Round 3 (`docs/benchmarks/mach64-215ct-486dx2-50-round3-2026-09-04.md`).
- **Startup got much slower this round, and it's not the diagnostic
  build's fault -- open item, not yet explained.** D2's own text-mode-
  to-gameplay transition took 92.6-105.8s; Round 1's comparable offsets
  (Round 1's B, low-tier audio) were 33-60s. The diagnostic
  instrumentation itself is negligible (RTC reader runs once at life
  start and once at exit, microseconds each; the `STAGEDBG.LOG` window
  emit is one small file write per 20s of play) -- doesn't explain a
  ~90s startup where Round 1 saw ~20-40s. Cold-boot vs. warm-boot state,
  or something in audio initialization on a freshly-powered PicoGUS, are
  both suspected but neither is confirmed. Not investigated further this
  round; recorded as open.
- No DPMI-paging evidence repeated from Round 1 checks (not re-verified
  every cell this round, but nothing else in the data points at paging
  either).

## Measurement method

Real hardware via vcctrl (authoritative), Gateway 2000 rig, `gateway2000`
profile. Sequence E0 (invalid), E1, D2, E2, F, each a natural life plus
the Round 1 two-Escape trailing life. Four wall-clock timestamps per real
life (launch, title-reappear, first Escape, second Escape); D2 and E2
additionally polled via `vcctrl_timeline` for the text-mode-to-title and
title-to-gameplay transitions specifically, at 15fps's request, to
separate startup/title-wait from the life interval itself.

Raw files now live tracked-adjacent at
`rawlogs/dx2-50-campaign-2026-09/round2/{E,E0,F,D2}/`
