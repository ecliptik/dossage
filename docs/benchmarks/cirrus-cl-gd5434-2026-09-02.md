## Results
Average FPS: **14.817881** (Passage's own `frameCount/netTime`, 4475
  frames / 302s -- `time(NULL)`-based, unaffected by the caveat below)
1% low: **not a trustworthy figure yet -- see Notes.** RUNMANIFEST
  reported `fps_p50=16.67`, `fps_p95=16.67` (identical at `%.2f` display
  precision); collected but not used for this verdict.
Simulation rate: locked at design target 15fps (`lockedFrameRate=15`,
  `game.cpp:96`); port is pacer-bound, not compute-bound, at this CPU
  tier (~24ms/frame idle slack against the 66.67ms budget -- see
  `docs/BENCHMARK-PLAN.md` Section 1 gate, unchanged by this run).
Audio underruns: not instrumented (no underrun-counting mechanism exists
  in this port). Two independent `vcctrl_audio_verdict` checks during the
  run (early, mid-run) both read `AUDIO_PRESENT`, music-like spectral
  shape, not a flat tone.
Peak memory: not measured (no instrumentation for this in the port).
Notes:
- **AUDIO-TIER MISMATCH BUG, found 2026-09-03 -- affects this run,
  correcting the record rather than leaving it implicit.** The committed
  `vendor/passage/gameSource/music/SONG.WAV` is the low-tier render
  (11025Hz mono, 2998844 bytes), but this build used `AUDIO_TIER=high`
  (22050Hz stereo). `musicPlayer.cpp` loads the WAV via `SDL_LoadWAV()`
  but never uses the returned spec -- `audioFormat.freq`/`channels` come
  from the compile-time tier constants instead, so a mismatched file
  plays at the wrong rate (that exact failure mode, "wrong-speed,
  wrong-pitch playback," is documented in that file's own code comment).
  Confirmed present on the physical target (`DIR` = 2,998,844 bytes) and
  in this build's `build/stage/`. **`AUDIO_PRESENT` below only confirms
  audio was playing, not that it played at the correct pitch/tempo.**
  **Correction, 2026-09-04**: this file originally predicted fps "is not
  expected to be affected" here -- that was wrong, not just unconfirmed,
  corrected rather than left standing. Round 1
  (`docs/benchmarks/mach64-215ct-486dx2-50-round1-2026-09-04.md`)
  measured a real, large fps effect from this exact audio-tier mismatch
  (~4.75fps between correctly-staged high- and low-tier builds) on
  486DX2-50, a CPU with little pacer slack. This leg's CPU (486DX2-66)
  has considerably more slack against the 66.67ms budget, so the same
  effect may be smaller here, but it was never independently re-measured
  on this CPU/card combination -- don't assume this run's recorded fps
  is unaffected just because the CPU has slack; treat it as untested,
  not confirmed clean. `build_sha12` does not cover this
  -- it hashes the vendor tree's committed (always-low-tier) file, not
  what actually gets staged, so this bug is invisible to the build
  fingerprint. Fixed and landed on `main` 2026-09-04 (merge `2881cfc`;
  patches `0036`, `0038`-`0041` -- `0037` was a temporary diagnostic,
  removed by `0038`; the `make stage` guard also landed).
- **PASS against the established Cirrus reference.** 14.817881fps is
  0.122fps from the ~14.94fps figure the pacer-tightening campaign
  established on this exact chip (prior build, pin untraceable -- see
  `docs/BENCHMARK-PLAN.md`), inside the pre-registered 0.3fps band. Per
  that doc's own re-baselining methodology, landing this close is also
  evidence the current build (with the RUNMANIFEST/`PORT_BUILD_SHA12`
  patch applied) is functionally equivalent to the prior validated build
  for real per-frame cost, not merely a pass in isolation.
- **fps_p50/fps_p95 are collected, not trusted, this run -- and the
  reason is now understood (corrects an earlier wrong guess in this same
  file's first draft).** Not a clock bug: `patches/passage/0034`
  captures `frameTime` as the window between the end of one iteration's
  pacer sleep and the start of the next's, i.e. pure work time
  (render + logic + audio pump), which the pacer always pads up to the
  66.67ms budget with sleep -- so 1/work-time is structurally never
  bounded by 15fps whenever there's slack, which this rig has
  (~24ms/frame, Section 1 gate). 60ms of work -> 16.67fps is exactly
  what that predicts, not corruption or a coarse clock. (The real-vs-
  DOSBox-X reject-rate gap, 24.0% vs. 60.4%, is still a true, separate
  observation -- confirms real hardware's clock is cleaner -- it just
  isn't what explains the clustering.) Fix, queued as patch `0035`, not
  yet landed: measure the full paced period (sleep-to-sleep) instead,
  which bounds instantaneous fps at <=15 in steady state and only
  exceeds the budget on a genuine stall -- the actual quantity a
  stall-catching percentile KPI needs.
- **Visual**: structural match to `docs/screenshots/dossage-gameplay.png`
  (character sprite position/pose, grass texture, path, sprite cluster
  and marker all present, nothing missing/swapped/garbled). Color values
  differ (path reads dimmer/more olive, greens spread across a narrow
  gradient rather than a few discrete values) -- attributed to this rig's
  analog-capture-plus-JPEG pipeline (a known, pre-existing characteristic
  of this capture path, not this run's rendering), since the underlying
  hue relationships (pure-green channel isolation, yellow-green path)
  hold in both. No corruption.
- **Post-exit black screen recurred.** ~20s of black/no-signal after a
  second in-game quit (Q) attempt, capture stick briefly lost lock
  (`state: frozen`), resolved via the rig's independent hardware camera
  to a clean `C:\DOSSAGE>` prompt underneath. Matches
  `docs/BENCHMARK-PLAN.md`'s already-documented "Post-exit black screen"
  known item -- recurrence noted per that item's own ask, not treated as
  a new finding.
- **The game does not exit on its own.** `playGame()` only returns
  `false` (ending the whole program) when Q/Escape/window-close is
  pressed; a natural age-based death fades to a static title card and
  then *automatically starts a new life* (confirmed from
  `game.cpp:2281-2286`'s `while(playGame())` loop in `mainFunction()`).
  This run's second RUNMANIFEST block (`duration_s=19`,
  `fps_p50=16.67`/`fps_p95=9.09`) is that auto-started second life, ended
  early by an operator-sent Q. Worth carrying into every future card's
  procedure: a full run needs an explicit quit keypress after however
  many lives you want recorded, not just waiting for the program to end.
- Card-identity correction mid-campaign: this run was originally briefed
  as the S3 ViRGE leg; a fresh rig scan (not the 57h-stale cache)
  confirmed the card actually installed is the Cirrus CL-GD5434. The
  ViRGE leg has not been run this campaign.

## Measurement method
Real hardware via vcctrl (authoritative), Gateway 2000 rig, `gateway2000`
profile. **Single run (one life's natural completion) -- not yet a
repeatability claim.** The 0.122fps delta from an already
multiply-measured reference (the pacer campaign ran this same chip
several times during its own investigation) is reasonable evidence
against regression, but a formal repeatability claim per
`docs/hardware-testing.md` would need additional repeat runs, not done
here.
