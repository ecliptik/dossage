## Results
Average FPS: **13.685015** (4475 frames / 327s). **No established
  reference exists for this CPU/build/card combination** -- the only
  prior 486DX2-50+Mach64 figure (~10.4-10.6fps) predates all pacer and
  percentile-telemetry work; not comparable. First datum.
1% low: RUNMANIFEST `fps_p50=16.67`, `fps_p95=9.09` -- **unchanged from
  every single prior run this campaign**, see Notes -- this is the
  headline finding.
Simulation rate: still nominally targeting 15fps, but see Notes -- this
  run is the first real evidence the port may no longer be purely
  pacer-bound at this CPU tier.
Audio underruns: not instrumented. Two `vcctrl_audio_verdict` checks,
  both `AUDIO_PRESENT`. No pitch/tempo observation this run (nobody was
  actively monitoring audio -- absence of a report, not a clean bill).
Peak memory: not measured.
Notes:
- **AUDIO-TIER MISMATCH BUG, found 2026-09-03 -- affects this run,
  correcting the record rather than leaving it implicit.** The committed
  `vendor/passage/gameSource/music/SONG.WAV` is the low-tier render
  (11025Hz mono, 2998844 bytes), but this build used `AUDIO_TIER=high`
  (22050Hz stereo). `musicPlayer.cpp` loads the WAV via `SDL_LoadWAV()`
  but never uses the returned spec -- `audioFormat.freq`/`channels` come
  from the compile-time tier constants instead, so a mismatched file
  plays at the wrong rate (that exact failure mode, "wrong-speed,
  wrong-pitch playback," is documented in that file's own code comment).
  Confirmed present on the physical target (`DIR` = 2,998,844 bytes) and
  in this build's `build/stage/`. **`AUDIO_PRESENT` below only confirms
  audio was playing, not that it played at the correct pitch/tempo.** fps
  is not expected to be affected (the audio-pump callback processes the
  same byte count per pump call regardless of what the bytes represent),
  not independently confirmed either. `build_sha12` does not cover this
  -- it hashes the vendor tree's committed (always-low-tier) file, not
  what actually gets staged, so this bug is invisible to the build
  fingerprint. Fix in progress (`15fps` session, patches `0036`/`0037`
  plus a hard `make stage` guard, separate `dx2-50-15fps` worktree, not
  yet landed in this tree).
- **A real, measurable regime change from the 66MHz results -- exactly
  as anticipated before this run.** All three cards at 486DX2-66 landed
  in a tight ~14.77-14.82fps band, expected because that CPU has real
  slack against the pacer's 66.67ms/frame budget (`docs/BENCHMARK-
  PLAN.md`'s own Section 1 gate: ~24ms/frame idle slack, measured on
  that CPU). **That gate explicitly says to re-check when the CPU
  changes ("the regime can shift between campaigns") -- it has.**
  13.685015fps at 486DX2-50 is a real, meaningful drop, and the life
  itself took genuinely longer in wall-clock time (`duration_s=327` vs.
  ~302-303s consistently at 66MHz) for the identical 4475-frame count
  (age-based death is frame-count-driven, not wall-clock-driven, so the
  frame count *should* stay fixed across CPU tiers -- confirmed). This
  is the first real evidence this port may now be genuinely CPU-bound
  rather than pacer-bound at this tier -- **not yet confirmed, the
  Section 1 compute-bound analysis has not been re-run for 486DX2-50,
  only flagged as needing it.** Don't assume either regime; measure it.
- **The bimodal pacing finding just gained its strongest evidence yet:
  fps_p50/fps_p95 are now confirmed CPU-clock-speed-independent, not
  just video-card-independent.** `fps_p50=16.67` (~60ms),
  `fps_p95=9.09` (~110ms) are bit-for-bit identical to every prior run
  this campaign -- three different video chips (Cirrus, ViRGE, Mach64)
  *and now two different CPU clock speeds* (66MHz, 50MHz -- a ~24%
  clock difference) all produce the exact same two values, despite the
  plain average moving by a full 1.1fps between the CPU tiers. This is
  hard to reconcile with any CPU-cycle-count-based mechanism (which
  would be expected to scale with clock speed) and is strong,
  independent corroboration of the leading hypothesis that this is a
  fixed-frequency **hardware timer artifact** (e.g. the PC BIOS/PIT
  tick, which runs off its own independent oscillator, not the CPU
  clock) rather than anything workload-, card-, or CPU-speed-dependent.
  Still not experimentally isolated -- the standalone
  `Time::getCurrentTime()`/pacer-timing probe remains the way to
  actually confirm the mechanism, but the case for it being a fixed
  hardware tick is now considerably stronger than "unconfirmed
  hypothesis."
- **Reject rate: 0/4475 -- the cleanest of any run this campaign** (prior
  runs: 0.22-0.27% on all three 66MHz legs). Not chased further here;
  plausibly related to the CPU no longer producing any frame fast enough
  to trigger whatever produces a near-zero/negative reading, consistent
  with (but not proof of) the regime-change read above.
- Visual/audio-pitch checks not repeated this run -- video-mode
  correctness was already established as CPU-independent on the 66MHz
  Mach64 leg, and no live audio monitoring happened this run.

## Measurement method
Real hardware via vcctrl (authoritative), Gateway 2000 rig,
`gateway2000` profile. Single run, first datum for this CPU tier -- not
a repeatability claim. **This run is outside `docs/BENCHMARK-PLAN.md`'s
originally-written scope** (which explicitly declined to sweep CPU:
"One CPU (486DX2-66)... there is no reason to re-sweep CPU") --
deliberate scope expansion, operator-directed 2026-09-03, into a
CPU x video-card matrix. See that doc's own CPU-matrix discussion for
what tiers remain (Am5x86-133, Pentium OverDrive 83).
